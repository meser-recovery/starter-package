# S10A full-service activation checklist (prepared, unexecuted)

This package replaces the Meser `gateway` and custom `caddy` application containers together. It must not edit HAProxy, Xray/REALITY, x-ui, MTProxy, n8n, router, DNS, firewall, secrets, GitHub App scope, or archive data.

1. Obtain explicit authorization naming the exact reviewed PR HEAD, source tree and generated full-service artifact hashes.
2. Independently verify the source SHA/tree, source archive, gateway image archive, Caddy/frontend image archive and release manifest.
3. Create and integrity-check an encrypted recovery bundle on a verified off-VM mount. Keep the age private identity outside the production VM.
4. Keep executable `capture-container-state.sh` and the reviewed `readiness.sh` beside `activate-reviewed-service.sh`. Use the validated full-JSON `docker inspect` snapshot to capture the current gateway/Caddy container IDs, image IDs, running status and exact health status; a container without a Docker healthcheck must record `health_status=not-configured`. Then create unique preserved rollback image tags and record Compose/Caddy/runtime, candidate image IDs and HAProxy checksums without printing secret values.
5. Keep both authorization gates in `activate-reviewed-service.sh` false until the separate review and authorization are recorded. Supply the smoke password only in a root-owned mode-0600 file.
6. Validate the candidate with `docker compose config` and the pinned Caddy image before replacement.
7. Replace only `gateway` and `caddy`; preserve Caddy volumes and never use `docker compose down`. Wait first for the exact gateway container/image to be running and healthy, then for the exact Caddy container/image to be running (`not-configured` health is valid), and only then probe the canonical public HTTPS route. The public probe uses a 90-second monotonic deadline, bounded connect/total timeouts, explicit startup-transient curl/HTTP allowlists and two consecutive `.ok=true` responses. Certificate, hostname, malformed-response and non-transient HTTP failures remain fail-closed.
8. Run the script's zero-write smoke: health, canonical unauthenticated redirect, one-password login, `/v1/session` replay, protected routes, automatic Archive access, Editor/config, exact read-only source-part bytes/SHA and logout.
9. Create and verify the post-activation off-VM recovery bundle before accepting the activation. Confirm the authoritative deployment record names its identity and records zero archive mutations.
10. On failure, `rollback-reviewed-service.sh <captured-rollback-directory>` force-recreates both prior application containers from the preserved references, waits for container readiness and the canonical public HTTPS route, then re-verifies both exact prior image IDs and proves neither candidate ID remains active. It does not derive the public service origin from a legacy captured runtime. Preserve `candidate-readiness.log` and `rollback-readiness.log`; a deadline timeout is an explicit failure with these sanitized per-attempt diagnostics retained.

The 2026-09-20 incident showed why both layers are required: the candidate gateway was healthy, but the first public probe ran less than one second after candidate Caddy started while HAProxy still marked its backend DOWN. The old rollback images were recreated and HAProxy marked the restored backend UP about three seconds after restored Caddy start, but the former rollback loop polled the legacy runtime origin and timed out despite the canonical route recovering. This is repository/incident evidence only and is not authorization for another production activation.

The superseded gateway-only scripts are hard-disabled. No command in this directory was executed against production during the repository stage.
