# S09B amendment — экран записи и основной сценарий архива

## Статус и область изменения

Этот amendment уточняет пользовательскую модель и компоновку уже определённого unified Zoom-recording UX. Он не изменяет каноническую модель данных, gateway API, хранение, правила версий, обработку аудио или границы Archive/Editor.

## Пользовательская модель

1. Основной объект аудиоархива — **одна запись Zoom**.
2. Исходные дорожки, проект обработки спикерской, версии для анонс-мейкера и финальные версии спикерской — материалы этой записи, а не самостоятельные библиотеки верхнего уровня.
3. «Подготовить для анонса» и «Обработать спикерскую» — два пользовательских намерения над одной записью.
4. Состояние рабочего списка и доступность исходников независимы и показываются отдельными статусами.

## Основной сценарий

1. Служащий на экране `Записи Zoom` находит встречу по названию или имени исходной дорожки.
2. Нажимает `Открыть запись`.
3. Общий список сменяется отдельным экраном выбранной записи; URL получает её канонический `session` UUID.
4. В первом смысловом блоке служащий выбирает дальнейшее действие:
   - `Открыть анонс-мейкер`; или
   - `Продолжить обработку` / `Начать обработку` спикерской.
5. При необходимости служащий ниже просматривает исходники и сохранённые версии этой же записи.
6. Действие `← Все записи` возвращает к прежнему списку, сохраняя введённый поиск и выбранные фильтры, и удаляет `session` из URL.

## Компоновка экрана записи

Порядок блоков обязателен:

1. Возврат `← Все записи`.
2. Компактная идентичность записи: название, дата/время, количество дорожек, происхождение и два независимых статуса.
3. `Что сделать с записью?` — две карточки пользовательских намерений с текущим состоянием и одной основной ссылкой каждая.
4. `Материалы записи` — последовательно:
   - исходные дорожки;
   - версии для анонс-мейкера;
   - финальные версии спикерской.
5. Контекстное восстановление, только если для этой записи есть незавершённая операция или состояние операций недоступно.
6. Управление метаданными и жизненным циклом.
7. Свёрнутые опасная зона и технические сведения.

На ширине до 767 px карточки намерений и элементы управления располагаются в одну колонку. На широком экране две карточки намерений располагаются рядом. Ни на одном поддерживаемом размере не допускается горизонтальное переполнение страницы.

## Обязательное поведение

- Список и экран записи не показываются одновременно.
- Заголовком экрана записи является пользовательское название встречи, а не общий текст `Сведения о записи`.
- Основные действия появляются раньше списков файлов и административного управления.
- Проект спикерской показывается в контексте действия `Обработать спикерскую`.
- Готовые версии остаются доступны при удалённых исходниках; недоступность новой обработки объясняется рядом с основными действиями.
- Удалённые и зарезервированные номера версий показываются без переиспользования и перенумерации.
- Воспроизведение, скачивание, удаление, восстановление и проверки целостности сохраняют существующие правила.

## Acceptance

1. Открытие строки скрывает общий список и показывает экран записи с её названием в `h2`.
2. Первый рабочий блок содержит ровно два намерения: анонс и спикерская.
3. Сохранённый проект спикерской приводит к действию `Продолжить обработку` и показывает дату сохранения.
4. Возврат в список восстанавливает видимость списка и сохраняет его локальное состояние.
5. Deep link с одним валидным `session` UUID открывает тот же экран без канонической записи в архив.
6. Экран проходит проверки на 320, 390, 768 и 1280 px без горизонтального переполнения.
7. Ни один read-only переход списка, записи или фильтров не выполняет запись в gateway.

## Не входит в amendment

- новые workflow, форматы или версии схем;
- изменение редактора и DSP;
- изменение gateway, GitHub Pages, production-конфигурации или архивных данных;
- автоматическое восстановление, удаление или изменение жизненного цикла записи.
